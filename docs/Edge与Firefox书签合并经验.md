# Edge 与 Firefox 书签合并经验

记录于 2026-09-07，2026-09-09 二次整理（见文末），基于一次真实任务：合并 Edge、Firefox 两边的书签，去重后同步回两个浏览器，再扁平化整理。任务全程用文件层手术完成。这条记录面向未来遇到同类需求的自己（人或者代理），按“机制认知、操盘细节、踩过的坑、可复现工具链”组织。

## 任务背景与数据事实

- Edge 书签文件：`~/.config/microsoft-edge/Default/Bookmarks`（Chromium 风格 JSON，version=1，含 `roots`、`checksum`、可选 `sync_metadata`）
- Firefox 书签库：`~/.config/mozilla/firefox/<profile>/places.sqlite`（本机 profile 名 `rwhlzot0.default-release`；壁 Firefox 的 profile 目录在 `~/.config/mozilla/firefox/` 而非 `~/.mozilla/firefox/`）
- 两边登录同一个邮箱账号（<1960171012@qq.com>），但分属两个云生态：Edge 走微软云、Firefox 走 Mozilla 云
- 初始规模：Edge 412 条记录（407 个唯一网址）；Firefox 902 条记录（只有 491 个唯一网址——profile 是从多处导入拼起来的，menu 与 unfiled 两棵根树完全相同，同一条洛谷题目最多存了 6 次）
- 归一化去重后的合并全集：532 个唯一网址（去 www、去尾斜杠、http/https 等价；仅差页面锚点 `#fragment` 的视为同一条）

## 核心机制认知（最重要的一节）

### 文件层手术与同步引擎是两套真相

浏览器书签的本地文件只是缓存，同步引擎持有服务器端状态。直接改文件时，浏览器关闭则改动落盘；重开后同步引擎会把本地改动与服务器状态做**并集合并**：

- 服务器旧条目（尤其是还持有旧数据的手机端上传过的）会被当作“新增”拉回本地，形成成批重复——这就是“被自动同步整成新旧混合”的根源
- 本地删除若无同步层的墓碑记录，会被服务器端旧数据覆盖——**文件层离线删除无法赢得同步引擎**（Edge 实测：保留 `sync_metadata` 期望删除以墓碑上传，失败，服务器旧树照常回流）

### 不同浏览器的稳定路径不同

- **Edge**：只有彻底断开收藏夹同步才稳定。在 `Preferences` 里改 `sync.keep_everything_synced=false` 且 `sync.bookmarks=false`（等价于 UI 里关掉收藏夹一项，其余同步类型不受影响）。重置同步（Settings → Sync → Reset sync）会清空微软云全部类型数据（含密码），本地会重新上传，但有丢失反馈案例，代价大
- **Firefox**：初次全量合并在第一次同步时发生一次；之后是增量同步，只拉“自上次同步以来有变动”的服务器记录。离线清掉的旧条目在服务器上无变动，不会被重新拉回——这是它与 Edge 的关键区别；但引擎级重置（退出重登、换设备）仍可能触发全量调和，理论上有回流路径
- **手机端**：本地还持有旧树，重新同步会把旧条目再上传。若合并范围不含手机（本任务明确不管），手机数据仍可能成为未来回流源

### 关于“不删任何内容”的语义

用户约束“只允许移动、新建文件夹、不删除”被明确为 **URL 级保留**：每个唯一网址至少一条存活，相同网址的重复记录合并为一条（标题取信息量最大者、添加时间取最早）。记录级保留会把历史导入事故（Firefox 的 411 条重复副本）完整复制给另一个浏览器。同 URL 不同标题的冲突通常极少（本次仅 3 例）。

## 操盘细节

### 通用流程

1. 优雅退出两个浏览器（SIGTERM，`pkill -TERM -x firefox`；正常退出保留会话恢复）
2. 完整备份：`places.sqlite` 三件套（main + `-wal` + `-shm`，WAL 模式下只拷 main 会缺未 checkpoint 的数据）、`Bookmarks` + `Bookmarks.bak`、`Preferences`、`Local State`，记录 md5
3. 在工作副本上做手术并断言，绝不直接改原文件
4. 提升前防漂移：`md5sum` 对比 live 与备份，浏览器进程确认已退出
5. `install -m 600` 落盘，清理 `-wal/-shm`，读回断言

### Edge：重写 Bookmarks JSON

- 新树结构：`roots.bookmark_bar`（收藏夹栏）+ `roots.other`（其他收藏）；`synced`（移动收藏）与 `workspaces_v2` 空根保留原样
- 节点字段：`type`（folder/url）、`name`、`guid`（uuid4）、`id`（全文件唯一字符串，从现有最大值递增）、`date_added`/`date_modified`（Windows 纪元微秒 = Unix 微秒 + 11644473600000000）、url 节点带 `url`
- `checksum` 省略安全：经 Chromium BookmarkCodec 验证失败时重算，不影响加载
- `sync_metadata`：整体换树时省略；原地去重且想保留同步关联则保留
- 同文件夹内可能出现同 URL 的兄弟重复（归一化相同但原始串不同，如尾 `?` 变体），需要按归一化键在文件夹内二次去重

### Firefox：SQL 手术改 places.sqlite

- 保留 `moz_places` 行不动：浏览历史与 favicon 都挂在上面，只重建 `moz_bookmarks` 层级
- 新网址需插入 `moz_places`：`rev_host` = 反转域名 + `.`（`example.com` → `moc.elpmaxe.`）；`url_hash` 的算法是带盐的 CityHash 变体，离线算不准，占位 0 无害（仅影响“已加书签”星标检测，首次访问后自愈）；`foreign_count` 最后重算（书签引用数，先置 0 再按引用置 1）
- 根节点：**不能硬编码 parent=1**——Firefox 维护任务会重建行号，`root________` 的 id 可能漂移（本机实测从 1 变成 593）。必须先按 `guid='root________'` 查 id，再查其直属区根；嵌套文件夹的清理条件必须排除 `parent=0` 的根自身
- 新版本 Firefox 根 GUID 变短（`toolbar_____` 而非 `toolbar________`），读区根一律按 guid 查、不硬编码
- 关键词（`moz_keywords`）与标签（tags 根）迁移前先查数量，为空则无需处理
- 事务内写完跑 `PRAGMA integrity_check` 与 `PRAGMA wal_checkpoint(TRUNCATE)`

### 同步回流的白名单去重

回流后最稳的收口是**白名单去重**：只保留批准集合（每个 URL 在其目标路径的唯一副本），其余全部清除。Edge 侧原地去重保留 `sync_metadata`；Firefox 侧 SQL 删除。注意作用域要覆盖全部根区（menu 根下也可能藏复活条目——分区断言会漏，必须加全局 `type=1` 计数断言）。

## 踩过的坑（全部以 bug 计入教训）

1. **dict 解包顺序**（出现三次）：写 `{guid: gid}` 时循环变量与被取列错位，把 id 当 guid 用。先在空表上打印确认，再批量写
2. **`set(dict)` 取键而非值**：`DELETE ... WHERE id NOT IN (set(dict))` 拿到的是一串 guid 字符串，整表被清空。工作副本隔离让这种事故零代价暴露
3. **`pgrep -f` 自匹配**：命令字符串包含被查进程名时匹配到自身 bash。用 `pgrep -x`（精确进程名）或 `lsof` 查文件占用
4. **管道退出码**：`grep 无匹配 | head | awk` 整条管道退出码是最后一个命令的（0），`||` 分支不执行，防御性 md5 对比变成空文件对比。把 grep 单独拿出来判断
5. **递归计数把文件夹自身算进书签数**：`WITH RECURSIVE` 的锚点行先计一次。要的是子树书签数，锚点应指向子行而非自身
6. **同步复活条目藏在没扫的根区**：分区走查全部通过、全局计数当场抓出 213 条残留。任何断言都要配一个全局总数
7. **检查脚本误报标准根**：`tags`、`mobile` 根正常为空，别把标准根当残留删

## 扁平化整理（一般用户的习惯区间）

- 一般用户书签栏的舒适区间：一级分类 5~12 个、单文件夹 30 条以内
- 纯展平会过载（本任务若 5 大类，编程开发 145 条一个文件夹）
- 平衡做法：把最大的子主题提升为一级分类，单文件夹封顶 ~73；最终采用 12 + 8（书签栏 12 类 + 其他书签 8 类），全部书签落在第二层（分类文件夹 → 书签），不再有嵌套
- 判定依据是数据：先统计每个文件夹的直属条数，再决定哪些子主题值得提升

## 二次整理（2026-09-09）：按添加时间分层 + 书签栏重分类

本次新踩的坑与新经验：

1. **URL 归一化不能丢 query**：微信文章的 path 都是 `/s`，差异全在 query 参数，去掉 query 会把不同文章判成同键。规则修正为：去 www、去尾斜杠、http/https 等价、去锚点，但**保留 query**
2. **`moz_bookmarks` 列名是 `lastModified`**，不是凭印象的 `dateModified`；动手前先 `SELECT sql FROM sqlite_master` 看 schema
3. **host 子串匹配不够用**：github 仓库类书签的差异在 URL 路径（`/jdhao/nvim-config`），host 全是 `github.com`；匹配域必须是 `host + URL path` 全文
4. **显式归位规则顺序敏感**：`bilibili.com` 的影音归位规则会误吃 B 站站内的 lua 教程（host 相同）；用来源夹限定（该条只对“学习”夹生效）消歧
5. **映射表驱动两边手术**：以归一化 URL 为键的单一映射 JSON 同时驱动 Edge JSON 重建与 Firefox SQL 移动，两边同构由构建方式保证，终验时逐路径对比两边 live 文件
6. **Firefox 原位移动套路**：按 guid 查根、`UPDATE parent/position/lastModified` 移动书签行、新夹 `INSERT`（手工生成 12 位小写字母数字 guid）、空壳夹确认无子行后 `DELETE`、夹 position 统一重排、`moz_places` 一律不动
7. **备份落持久目录**（`~/Workspaces/bookmarks-backup-20260909/`），不再放 `/tmp`——上次的备份和脚本随重启全丢，这次全部重做了一遍侦查
8. **边界条目按内容主题就近归位**并列入报告：BMS SEARCH（游戏夹里的 BMS 工具站归 BMS）、B 站主站（学习夹归影音娱乐）、Phoronix（Linux 硬件资讯归系统与桌面）、FFmpeg 教程（游戏夹归编程杂项）、ivy extension 页（主题不明归编程杂项，低置信标注）

两个新教训：

1. **落盘后浏览器被打开过，防漂移 md5 对比失效**：places.sqlite 因浏览历史必然变化，不能再用文件 md5 证明“没被动过”；改用**结构走查断言**——把 live 书签树与上一版映射表逐路径对比，树层未动即可安全手术。拷贝改用 sqlite3 的 backup API，自动合并 wal 里的数据
2. **手术范围收缩时移动循环必须过滤桶**：只动书签栏的手术，遍历桶时漏过滤把其他书签 160 条也当成了移动目标，靠 moved 计数断言当场拦下——任何“动了多少条”的预期都要写成断言

## 四次调整（2026-09-11）：全量二级分类

在五大域稳定态之上做的第四次手术：收藏夹栏一级分类不变，各文件夹内部拆二级分类。书签栏 5 类、其他收藏 7 类、归档区 5 个子夹全部拆分为主题子夹（共 62 个，归档区因此出现第三层）；数码（1 条）与杂项旧档（5 条）保持平铺；子夹内保持原相对顺序；两边同构、URL 级保留（532 条零变化）。结构决策照旧由盘问流程逐项确认，红队自攻补出两条前置规则：子夹内顺序（保持原相对顺序）、基线漂移策略（新增条目自动归位、删除不复活）。

本轮的新经验：

1. **工具链与备份全部落持久目录**（`~/Workspaces/bookmarks-backup-20260911/`，下分 scripts、mapping、report、original、work），兑现上次“不再放 /tmp”的教训；全流程脚本可重跑
2. **序号映射作为规格中间表示**：先从 FF 快照导出各文件夹的编号清单（`report/ff-numbered.txt`），方案以“文件夹加序号列表”写进构建脚本，由脚本断言：路径集合一致、每个序号恰好用一次、总数 532、归一化 URL 全局唯一。比直接写 URL 列表可核对性好得多，改归属就是改序号
3. **平铺文件夹也要登记进映射**：不拆分的文件夹（数码 1 条、杂项旧档 5 条）其条目必须进映射表，否则总数断言对不上；“不拆分”不等于“不进映射”
4. **中间层容器要识别**：“2023 前归档”自身不直挂书签、只有子夹；按“含直挂书签”过滤后再做路径集合断言，否则误报路径不一致
5. **两边既有顺序差异要预判**：Edge 与 FF 在 8 个文件夹里条目顺序本就不同（历史导入差异），本次按各自原序落位、不强行对齐；终验只对集合与路径断言，顺序差异写入报告
6. **终验新增三个维度**：FF 侧检查 position 连续性（每个父夹应为 0..n-1）、type 分布（只应有 1 与 2）、空文件夹（排除标准根 menu/tags/mobile——上轮教训的再次应用）
7. **防漂移的基准是执行前快照**：Edge 的 Bookmarks 会被浏览器会话保存重写（本次 19:45 的 md5 与目录内旧备份不同），只要快照晚于最后一次写入，md5 对比仍有效；FF 则只能用结构走查（浏览历史必然变化）
