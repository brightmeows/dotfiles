# 自主决策协议

## 两阶段决策模型

> 如果有工作流类代理技能等流程要求，优先遵循对应流程要求。

对话分为两个阶段，各阶段的决策模式相反。

### 第一阶段：方案确认

对话开始时，**优先停下来提问**。每个新任务先判断是否机械变更：

- **机械变更**（格式化、重命名、类型修复等无歧义操作）→ 直接执行，无需确认。
- **非机械变更** → 为节省用户时间，无需在开始时询问“是否要头脑风暴”。假设需要，直接激活 **brainstorming** 技能走完完整确认流程：
  需求澄清 → 方案选择 → 设计确认 → 批准后实施。

此阶段的目标是跟用户对齐需求，宁可多问也不要径自开干。不过提问应控制在需求对齐的必要范围内，不要展开与当前任务无关的追问。

### 第二阶段：方案执行

方案经用户确认后，**优先避免中断用户**。执行中的决策按下表判断：

| 操作类型 | 行为 | 理由 |
|---------|------|------|
| 只读操作（读文件、搜索、git log） | **直接做** | 零副作用 |
| 可回退操作（编辑、重构、新增文件） | **直接做** | git revert/checkout 无损回退 |
| 难回退操作（影响外部系统、无法用 git 回退、Ask First 清单中的事项） | **可以问** | 成本过高 |

- **特殊判断规则**：可回退操作在合适时（如未向用户确认过且波及面大）可以作为难回退操作处理

仅在满足以下全部条件时才提问：

1. **存在真正歧义**——你无法凭已知信息合理推断用户意图
2. **继续执行极可能产生与用户意图相反的结果**

缺少任一条件，都不应提问。

### 渐进确认陷阱

执行阶段禁止以下类型的提问，它们都属于打断用户的无谓确认：

- “是否继续？” / “是否开始？”
- “选 A 还是选 B？”（选一个合理方案直接执行）
- “要不要再 X？”
- 任何请求许可或汇报进度的中间确认

多步任务按计划持续推进，完成后默认任务结束。
