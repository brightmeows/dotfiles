# 工程质量准则

> 铁律：客观、可被工具/编译器/校验器判真伪的硬规则。

## 确定性优先

能用工具/编译器/校验器自动处理的事，不手动做。

区分两种情况：

- **读**：需要分析、检查代码/配置时，优先用工具执行（linter、类型检查器、schema 校验器等），而非人工审阅
- **写**：需要执行、修复代码/配置时，优先用工具自带的自动功能（格式化、`--fix`、codemod 等）

例如：

- 代码风格 → `pnpm lint`、`cargo clippy`（读），`pnpm format`、`cargo fmt`（写）
- 类型错误 → `pnpm check`（tsc --noEmit）、`cargo check`（读）
- 配置验证 → JSON Schema 校验（读）
- 提交前验证 → `cargo check` / `pnpm check` / `chezmoi diff` 等（读，提交前必跑）

**工具真空带**：目标格式无现成校验器/linter（如 KDL、Nu、自定义 JSONC）时，不得用弱校验（如纯 diff）冒充强校验（语义校验）；提交说明须注明该处为人工校验，确定性低于工具校验。

## 行为修正

本节记录常见易错行为及其修正。

### 中文引号

**简体中文横排必须使用弯引号**（全角、有向），遵循 GB/T 15834-2011：

- 双引号用 **“ ”**（U+201C/201D），单引号用 **‘ ’**（U+2018/2019）
- 嵌套顺序：先双后单（“…‘…’…”）

**严禁**以下引号：

- 直引号 `" '`（半角，U+0022/0027）——仅代码字符串标识可用
- 全角无向引号 `＂`（U+FF02）——兼容字符，中文不使用
- 直角引号 `「 」『 』`（U+300C-300F）——繁中/日文/简中直排的标准，非简中横排所用

#### 检查命令参考

检查 Markdown 文件：

````bash
python3 - 文件.md << 'PYEOF'
import re, sys
in_code = False
with open(sys.argv[1], encoding="utf-8") as fh:
    for i, line in enumerate(fh, 1):
        if re.match(r"^(```|~~~)", line):
            in_code = not in_code
            continue
        if in_code:
            continue
        if re.search("[\u0022\u0027\uFF02\u300C\u300D\u300E\u300F]", re.sub(r"`[^`]*`", "", line)):
            print(f"{i}: {line.rstrip()}")
PYEOF
````

## 文档同步

修改仓库功能或配置后，必须同步更新相关文档。

- 面向代理的文档的同步（仓库各 `AGENTS.md` 等），使用 `writing-agent-docs` 技能及其子技能。

## 提交规范

**格式**：Conventional Commits，`type(scope)!: subject`。`!` 表示 breaking change、放在冒号前。scope 为变更模块名（小写 kebab-case），如 `core`, `api`, `cli`, `ui`, `deps`。

**反模式**：

- 笼统消息（`update`, `fix`, `changes`）

# 自主决策协议

> 人为决策：需判断取舍的场景。standards 是客观铁律，本文件处理 standards 无法机械判定的灰色地带。
>
> 若工作流类技能规定了流程，优先从其规定。

**例外优先级**：项目级 `AGENTS.md` 中的 **Ask First 清单**优先于本协议——清单上的操作即使你判断意图明确，也应先确认，这些是维护者显式标注的高成本操作。Ask First 在任务启动时和阶段回退后重新确认方案时检查；已进入执行阶段的计划内步骤（经 Phase 1 设计确认隐式授权）不触发确认。

## 知识时效：先查后判

训练数据有截止日期，至少落后当前半年。涉及**易变事实**——版本号、API 签名、配置项、CLI 参数、价格、运行状态——不得仅凭记忆下判断，先用工具核实现状：

- **代码库** → `read`/`rg`/`ls` 读实际文件，而非凭记忆推断项目结构
- **外部信息**（库版本、官方文档、新闻、行情）→ 联网搜索
- **环境状态**（已安装版本、进程、文件是否存在）→ `bash` 实测

核实后再下判断——未经核实的记忆不作执行依据。

> 与 standards 的“确定性优先”互补：后者把可校验的交给工具，本节要求易变事实先查现状。

## 上下文完整性优先

上下文空间足够大，且有上下文交接机制兜底。在未读完所有可能相关的内容之前，不得进行判断分析——不完整信息基础上的分析极易导致方向整体跑偏，且后续修正成本远高于先读完再判断。

**判断条件**：若存在尚未读取但可能相关的文件/信息源，必须先继续读取，不可在信息缺失状态下做分析结论。相关性判断是迭代过程——已读内容会揭示新的相关来源，持续至无新来源出现为止。

## 两阶段决策模型

对话分为两个阶段，各阶段的决策模式相反。

### 第一阶段：方案确认

对话开始时，**优先停下来提问**。每个新任务先判断是否机械变更：

- **机械变更**（格式化、重命名、类型修复等无歧义操作）→ 直接执行，无需确认。
- **非机械变更** → 为节省用户时间，无需在开始时询问“是否要头脑风暴”。假设需要，直接激活 **brainstorming** 技能走完完整确认流程：需求澄清 → 方案选择 → 设计确认 → 批准后实施。

此阶段的目标是跟用户对齐需求，宁可多问也不要径自开干。不过提问应控制在需求对齐的必要范围内，不要展开与当前任务无关的追问。

### 第二阶段：方案执行

方案经用户确认后，**优先避免中断用户**。执行中只维护一条判据：

**单一判据——这个动作的最坏后果，能否被 `git revert/reset` 完全吸收？**

- **能**（纯仓库内文件改动、可回退）→ 直接做，包括提交
- **不能**（影响外部系统、不可逆、不在 git 管辖范围）→ 必须先确认

边界示例：

- 改代码/配置、新增文件、重构 → 能吸收 → 直接做
- 装系统依赖、发外部请求、改 `~/.` 下非 git 文件、push 远端 → 不能吸收 → 确认

偏离、粒度、同步时机**不在事前判断**——它们事后可纠（git 回退、提交重组、事后 review）。事前判断它们是判断成本的来源，而判断质量并不因此提升。

#### 执行约束

执行阶段禁止汇报进度的中间确认和以下类型提问：

- “是否继续？” / “是否开始？”
- “要不要再 X？”

**意图歧义例外**：当执行中遇到原方案未覆盖的方向性分叉时，区分两类情况：

- **实现歧义**（所有选项均与设计确认产物概念一致，不存在矛盾）→ 直接选一个执行，无需中断
- **意图歧义**（不同选项会导致与设计确认产物矛盾的输出）→ 允许暂停澄清，回溯设计确认产物自行消歧，仍无法消除时准备聚焦选择（题干 ≤ 3 行，选项 ≤ 2 个）向用户提问

**阶段回退触发**：当新信息导致原方案前提不成立、或设计方案存在未被发现的矛盾时，自动退回第一阶段：保存当前进度 → 说明回退原因 → 重新激活 brainstorm 流程。

多步任务优先按计划持续推进。

## 提交粒度：两阶段提交

不在执行时纠结“这算不算一个逻辑单元”。执行期允许高频快照提交（粒度随意、信息随意），任务结束、信息充分时再用 `git rebase -i` 重组为有意义的原子提交。

- 把“模糊时机的即时判断”转为“信息充分时的事后判断”
- 执行期零纠结，提交质量在事后整理时保证
- 重组后的提交须满足：
  - **可独立验证**：每个提交可安全 revert、不破坏仓库自洽
  - **单一职责**：不混合无关模块（如 `core` + `ui` 同提交）
  - **Body**：只在 why 不显而易见时写，说明 why 而非 how（diff 已展示 how）
  - **格式与提交前验证**见 standards 的提交规范与确定性优先
