# 编码助手行为规则：主代理专用

## 对话开始时

先判断当前请求是否机械变更；若非机械变更，激活 **brainstorming** 并走完整方案确认流程（需求澄清 → 方案选择 → 设计确认 → 批准后实施）。

## 关于停下来提问用户

> 如果有工作流类代理技能等流程要求，优先遵循对应流程要求。

只问一种情况：**存在真正歧义，继续工作会产出与用户意图相反的结果**。

拿不准时按顺序判断：

1. **只读操作**（读文件、搜索、git log）→ 不改变任何东西，直接做。
2. **可回退操作**（文件编辑、重构、新增文件）→ `git revert` / `git checkout` 可无损回退，直接做，错则改。同样考虑恢复成本，回退成本过高的操作建议作为难回退操作处理。
3. **难回退操作**（影响外部系统、无法用 git 回退，或属于 Ask First 清单中的事项）→ 可以问。

### 渐进确认陷阱（仅限只读操作和可回退操作）

只读操作和可回退操作中，不要在任何阶段询问“是否继续”“是否开始”“选 A 还是选 B”“要不要再 X”——这些请求许可的提问都默认不需要问。多步任务按计划推进，可选方案直接选一个合理方案执行，完成后默认任务结束。

## 提交规范

- **即完即提（原子提交）**：每完成一个逻辑单元后立即提交，确保每个提交只做一个变更。如果描述里必须用“和”/“以及”连接，就该拆分。工作流：工作 → 提交 → 工作 → 提交 → …，不累积变更到最后一并处理。
  - **忘了及时提交时**：能拆就拆（`git add -p`），拆不干净就整体提交并在 body 写明变更清单；核心是“现在就提”优先于“等想清楚怎么拆”。
- **可独立验证**：每个提交可安全 revert、不破坏仓库自洽。
- **格式**：Conventional Commits，`type(scope)!: subject`。`!` 表示 breaking change、放在冒号前。scope 为变更模块名（小写 kebab-case），如 `core`, `api`, `cli`, `ui`, `deps`。
- **Body**：只在 why 不显而易见时写，说明 why 而非 how（diff 已展示 how）。
- **反模式**：
  - 混合无关模块（如 `core` + `ui` 同提交）
  - 笼统消息（`update`, `fix`, `changes`）
  - 提交前不跑验证（`cargo check`, `pnpm check`, `chezmoi diff` 等）
