## 确定性优先

### 演进历程

- **v1**：单一“工具验证优先”——能用工具 / 编译器 / 校验器自动处理的事就不手动
- **v2（2026-08-07）**：升维为两层统领原则——**建模优先**（理解层，原理兜底）+ **可验证优先**（验证层，机制兜底）

升维动因：v1 只覆盖执行 / 验证层（“做对了吗”），缺失理解层（“在解正确的问题吗、用的是不是已知最优方法”）。两层同属“确定性”概念的不同层次，故升维为一个统领原则而非新增并列节（M.1 升维表述）。

### 设计决策

#### 为什么是“两层确定性”而非独立原则

确定性 = 从理解到验证都追求“可推导、可复现、不依赖直觉和记忆”。建模优先与可验证优先是同一概念的递进层次（理解 → 验证），拆成并列节会割裂内在逻辑、增加 token。

#### 建模优先的核心：显式化隐含假设

建模的本质 = 把隐含假设显式化（“我默认 X 成立” → “X 是否成立、在什么条件下成立”，从而可审视、可证伪）。学科模型 / 形式化模型 / 失效建模都是显式化假设的工具。

- 命中 LLM 痛点：AssumptionMiner 专门研究 LLM 代码生成的隐含假设问题（见理论出处）
- 统领性：用“显式化假设”作为元本质，比单说“映射到学科模型”更普适

#### 三类建模维度

| 维度 | 例子 | 定位 |
|---|---|---|
| 学科模型 | 控制论 / 排队论 / 优化论 / 分布式理论 | 自动控制原理、数学、计算机科学理论的代表（学科级，勿降为具体技术）|
| 形式化建模 | 类型系统 / 状态机 / 不变量 | 让非法状态不可表示，设计期结构性保证 |
| 失效建模 | 故障模式（FMEA）/ 错误传播 / 降级路径 | LLM 最常漏的关注点；与可验证优先互补（正常路径 vs 异常路径）|

#### 可验证优先：为什么从“工具验证”升维为“可验证”

- “工具”是手段会过时（M.1），“可验证”是判断标准不过时
- “可验证”涵盖“自己造验证机制”（校验脚本 / 断言），比“工具”更宽，呼应工具真空带
- 优先级排序：类型检查 > linter / schema > 测试断言 > 量化指标 > 人工判断（类型既是形式化建模，又是最强编译期验证，故排最高）

#### “何时建模”子节：防止过度建模与漏建模

First Principles 不该滥用——过度建模和漏建模一样糟。给“该建模 / 直接动手”的判断标准（系统属性 vs 常规任务）。

### 理论出处

| 概念 | 出处 | 核心论点 |
|---|---|---|
| First Principles Thinking | Scaler《First Principles Thinking: The Skill That Makes 10 Years of Experience AI-Proof》；Addy Osmani《First Principles for Software Engineers》(2022) | 经验 = 类比，AI 让“凭经验”贬值；从基本原理推导不贬值 |
| First-Principles Modeling vs 数据驱动 | Kiss & Grievink, TU Delft, *Ind. Eng. Chem. Res.* 2026 (doi:10.1021/acs.iecr.5c04156) | FPM 保证可解释性 / 可靠外推，数据驱动只擅长插值 |
| 控制论应用于计算系统 | Abdelzaher / Diao / Hellerstein / Lu / Zhu《Introduction to Control Theory and Its Application to Computing Systems》| ad hoc 设计 → 震荡 / 不稳定；控制论 → 稳定 / 精确 / 收敛（TCP / SQL Server / FFTW / ATLAS 均为控制论产物）|
| 自整定（self-tuning）| Wikipedia《Self-tuning》| 控制论概念在计算系统的广泛应用 |
| 把隐含假设显式化 | Enterprise Craftsmanship《Making implicit assumptions explicit》| 软件原则 |
| LLM 隐含假设（学术痛点佐证）| AssumptionMiner, arXiv:2607.22898 | LLM 代码生成中的隐含假设挖掘、追踪与修订 |
| FMEA（故障模式与影响分析）| Wikipedia / ISO | 失效建模的成熟标准方法 |
| 4+1 视图模型 | Kruchten, *IEEE Software* 1995 (doi:10.1109/52.469759) | 多视图分别建模不同 stakeholder 的 concerns |
| ISO/IEC/IEEE 42010:2022 | 架构描述国际标准 | viewpoint / view / concern 三元组（4+1 的标准化、通用化）|

### 考虑过但未纳入（避免重开已决议题）

| 方案 | 否决理由 |
|---|---|
| 4+1 / ISO 42010 完整多视图框架 | 完整术语属通用知识（A.3，LLM 预训练里有）；只取其“失效是常漏关注点”的洞察，已由失效建模 bullet 承载 |
| 类型单独成层（type-driven development）| 类型是建模与验证的交汇点，硬拆成独立中间层割裂本质；在建模优先点名（形式化建模）+ 可验证优先排最高优先级，点名两次更有效 |
| 学科模型映射速查表（工程问题 → 学科）| 穷举不完 + 具体技术会过时（违反 M.1 / A.4）|
| 领域 / 概念建模 | 偏需求分析，普适性低于失效建模，留给具体项目 AGENTS.md（避免全局 Context Bloat）|
| 交互 / 并发 / 契约建模独立成类 | 大部分能被“形式化建模（不变量 / 状态机）+ 学科模型（分布式理论）”召唤，不单独成类 |
| 失效建模升级为独立子节 | 与学科 / 形式化同属并列维度（建模的三类对象），放同一组 bullet 最自然；“何时建模”子节管触发时机，职责不同 |

## 语言风格

### 符号克制（2026-08-10）

- 动因：inline-context 扩展工具行输出 `rg→grep` 箭头符号，主人要求改用文字“替代”；同时要求在全局指令提示不用 emoji / 符号装饰
- 决策：语言风格节新增“符号克制”条目——不用 emoji、箭头、勾叉等装饰符号，用文字表达（示例：rg 替代 grep）
- 否决：不配套检查脚本——emoji 检测正则复杂易误报，投入产出低；若后续反复出现再议（A.1 增量迭代）
