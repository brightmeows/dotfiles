# 盘问（Grilling）

像面试官一样持续盘问用户，直到双方达成共识。本技能先规定**一轮问答长什么样**（输出规范），再说明**如何推进**（运行机制）——执行时先对齐输出，再跑机制。

## 一轮问答长什么样

每轮由若干条**推导决定（D 系列）**与若干个**问题（Q 系列）**组成，D 列在问题之前。问题格式：

```
**Q1** - **<问题标题>**：

**背景**：<已查明的、与本问相关的信息与约束>

<问题正文，可以是多段>

- **A <选项名>**：<做什么>；<影响：用户可感知的结果与生态>；<代价：放弃的东西>
- **B <选项名>**：<同上>

**推荐答案**：<你的推荐与理由>
```

推荐答案引用选项时写“推荐 A：理由”。确实没有明确倾向时写“无倾向”并简述各选项利弊，禁止静默省略。

**编号纪律**：问题编号 Q1、Q2…全局连续递增，不跳号不复用；问题内多个选项统一用 A、B、C…编号；引用前置结论写“Q{m} 的结论”，不复述旧问题。

## 信息质量标准

一轮问答的完成标准：**用户不追问就能作答**。逐条：

1. **背景必带**：凡是已查明的、与本问相关的信息与约束，随题在“背景”块交出，与本问无关的不塞。查了不报算违规——让用户自己翻文件、回忆上下文来答题，就是把查信息的职责推回给用户。
2. **选项展开**：每个选项写清三要素——做什么、影响（用户可感知的结果与生态）、代价（放弃的东西），利弊就融在三要素里。只写选项名不算展开。
3. **理由落地**：推荐理由必须落到机制与代价——为什么选它、放弃其他选项损失什么、损失能否补回。“推荐 A，因为更稳”这类空话不合格。
4. **毛边自纠**：若你的推荐其实是反驳问题本身的措辞（同意推荐等于对问题答“否”），须显式说明，并给出修正后的问法。

## D 系列：推导决定

**定义**：D 是从已敲定回答与已查明信息中**逻辑推导**出的结论——无需再问，但必须让用户知情。编号 D1、D2…与 Q 系列独立递增。格式：

```
**D1** - **<决定标题>**：<结论>。推导链：因 <前提一>，且 <前提二>，故 <结论>（由 Q{m} 推导）
```

推导链必填：列出从前提到结论的推理步骤，让用户能复核，不许只标来源。

**判定——什么算“纯粹推导”**：主测试是**换人测试**：换一个理性的用户来答，答案会因偏好或取舍而不同吗？会不同，归 Q；任何理性用户答案都相同，归 D。**拿不准一律归 Q。**两条从属测试：

- **可逆性**：双向门决策（可逆、回退成本低）倾向 D；单向门（难以逆转）必 Q。
- **显著性**：影响设计树后续分支或系统结构的必 Q；不影响后续的叶子决策倾向 D。

常见误分类判例：

- **实现细节选型**：两个方案用户可感知的结果无差别（换人测试通过）时可 D；有代价差异必 Q。
- **偏好外推**：从用户已敲定的选择外推配套决策（“用户选了 A，那 A 的配套也照做吧”）——外推引入了用户未确认的假设，归 Q；除非配套完全无取舍。
- **依赖未明说前提**：默认值、行业惯例、常识都是未敲定的前提。有取舍时把前提升格为新的 Q 走查；无取舍时可 D，但推导链中必须显式列出该前提。

**披露纪律**：D 在它产生的当轮立即随问题披露，列在问题之前，禁止攒到收尾才统一提出。D 默认采纳，用户可指出异议；若被推翻，把推导链中未明说的前提升格为新的 Q 重新走查。

## 运行机制：设计树、轮次与前沿

把整个盘问过程映射为一棵**设计树（design tree）**：每个决策都会分叉出挂在它之下的子决策。

以**轮（rounds）**为单位推进这棵树。**前沿（frontier）**指所有前置条件已经敲定的决策——也就是你**现在**就能问的问题，不必猜测你还没听到的答案。一轮可以只问一个问题，也可以把若干前沿问题合并问，自行分组。同一轮的问题必须互相独立——有依赖时，被依赖的先问，依赖方留到更晚的轮次。给每个问题编号并附推荐答案，等用户答完一整轮再进入下一轮。

每一轮，用户的回答都会重塑这棵树——已敲定的决策把前沿向外推，解开依赖它们的后续问题。重新计算前沿，进入下一轮。

## 信息与决策分工

查**信息**是你的职责，绝不是用户的。这里的“信息”泛指一切需要获取的内容——既包括环境中的事实，也包括外部知识。当前沿问题需要这类信息时，自己去查清楚（按环境能力选用工具、子代理或并行探查）——凡是能自己查到的，都别去问用户。不要卡在它上面：一次进行中的探查是一个未敲定的前置条件，因此只有它下游的问题才要等探查完成——本轮先问前沿中不依赖探查的问题，依赖信息的留到探查完成后的下一轮再问。**决策**属于用户——逐条抛给他们，然后等待。

信息查清只解开下游问题的前置条件，不等于那些问题已被回答：依赖信息的决策若含用户偏好或取舍，仍要作为 Q 逐条问，禁止用查到的信息替用户敲定；只有换人测试通过的结论才可归为 D。

## 优先用结构化提问工具

若环境提供结构化提问工具（如 `questionnaire`、`question`），优先用它呈现整轮问题，不可用时回退纯文本。配套约定：

- **正文先行**：调用工具前，正文按上面的格式完整列出本轮的 D 与 Q（含每问推荐答案），工具只作点选入口。
- **选项带推荐提示**：选项的 description 里注明推荐标记与理由；工具装不下的展开内容（如三要素全量）以正文为准。

## 示例：一轮合格问答

```
**D1** - **TOML 解析用现成 crate 而非手写**：两方案用户可感知的结果无差别（同样产出解析后的配置结构），属实现细节选型。推导链：因 Q1 已选定 TOML 格式，且成熟 crate 的解析正确性由测试套件保证，手写无收益，故直接用 crate（由 Q1 推导）

**Q2** - **配置文件位置**：

**背景**：已查明目标平台为 Linux 与 macOS；同类 CLI 工具的主流做法是 ~/.config/<tool>/，少数用 ~/.toolrc；本工具在 systemd 用户服务下也会被调用。

配置文件放在哪里？

- **A ~/.config/tool/config.toml**：遵循 XDG Base Directory 规范；chezmoi、备份工具、systemd 沙箱等生态都按 XDG 路径找配置；代价是路径较深，手改稍不便
- **B ~/.toolrc**：单文件直白，dotfiles 管理者一眼可见；代价是偏离 XDG，systemd 用户服务 HOME 指向不一致时会读不到配置

**推荐答案**：推荐 A：XDG 路径被 systemd 与主流配置管理工具识别，B 的沙箱读不到问题是真实故障源；放弃 B 的“单文件直白”可由后续加 tool config 子命令补回。
```

## 完成与收尾

当前沿为空时，会话才算结束：所有探查均已完成、依赖信息的下游 Q 均已问过，设计树的每个分支都已走查过，没有留下任何被默默假设的东西。此时停下，把已敲定的决策列成**按领域分组的清单**：每个主题分支一组，组内 Q 按编号排列，D 跟在它依赖的 Q 后面（D 已在当轮披露过，此处仅汇总）：

```
## <领域一>

- **Q1** - <结论>
- **D1** - <结论>（由 Q1 推导）
- **Q4** - <结论>

## <领域二>

- **Q2** - <结论>
- **Q3** - <结论>
```

收尾确认不可跳过——即便信息已查明、选项看似唯一，也须把清单交用户确认。请用户确认共识，并让用户选择下一步：开始实施 / 继续盘问 / 调整决策。用户做出选择前，不要基于共识采取行动。
