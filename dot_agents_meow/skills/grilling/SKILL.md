# 盘问（Grilling）

## 概述

像面试官一样持续追问用户的计划、决策或想法：沿着决策树的每个分支走查，逐个解开决策间的依赖，直到双方达成共识。每个问题都附上推荐答案，一次只问一个。

## 何时使用

| 触发场景 | 示例 |
|----------|------|
| 用户想压力测试想法 | 说出“grill 我”“拷问拷问这个方案”等触发语 |
| 动手前想先对齐需求 | 方案涉及关键决策、计划尚未想清楚 |
| 决策树有多层依赖、容易漏掉分支 | 大计划、多步骤任务、跨模块改动 |

## 核心规则

| 规则 | 要求 |
|------|------|
| 一次一问 | 每次只问一个问题，等用户回答后再继续。一次问多个会让用户无所适从 |
| 编号统一 | 每个问题以 `Q1`、`Q2`……编号，从 1 开始递增，不跳号、不复用 |
| 事实自查 | 能通过探索环境（文件系统、工具、搜索）查证的事实，自己查，不问用户 |
| 决策归用户 | 偏好、取舍、目标等决策属于用户，逐条提问并等待回答 |
| 附带推荐 | 每个问题都给出推荐答案，用户可据此快速决策 |
| 未确认不动手 | 用户明确确认达成共识前，不执行任何操作 |

## 编号格式

- 格式固定为 `Q{n}`，n 从 1 开始连续递增
- 每次提问只带当前编号；用户回答后，编号推进到下一个
- 引用前置结论时写“Q{m} 的结论”，不复述旧问题
- 跳号、复用编号、无编号的问题均为违规

## 提问模板

每个问题按固定结构输出：

```
Q{n}：一句话说清问题

- 背景：为什么需要这个决策（一句话）
- 依赖：所依赖的前置决策（引用 Q{m} 的结论；无则省略此行）
- 推荐：推荐答案及理由
```

示例：

```
Q3：发布流程要不要接入 pre-commit 检查？

- 背景：Q1 确定采用 chezmoi 管理点文件，Q2 确定单人维护
- 依赖：Q1、Q2 的结论
- 推荐：接入。仓库已有 .pre-commit-config.yaml，pnpm lint 已是维护惯例
```

## 事实与决策分工

| 类型 | 归属 | 处理方式 |
|------|------|----------|
| 事实（环境状态、文件内容、命令行为、历史记录） | 代理自查 | 读文件、跑命令、搜索，不问用户 |
| 决策（偏好、取舍、目标、范围） | 用户 | 逐条编号提问，等待回答 |

## 完成标准

- 决策树全部分支走完，依赖全部解开
- 用户明确表示达成共识
- 达成共识前不执行任何操作；共识后按确认的方案行动

## 常见错误

| 错误 | 修正 |
|------|------|
| 一次抛出多个问题 | 只问当前编号的一个问题，等回答再推进 |
| 问可自行查证的事实 | 先查环境再提问，问题只留给决策 |
| 编号跳号或格式不统一 | 严格按 `Q1`、`Q2`… 连续递增 |
| 未给推荐答案 | 每个问题必附推荐，用户可据此快速决策 |
| 未确认就动手 | 达成共识前只提问、只查证，不执行 |
