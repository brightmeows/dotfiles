# 盘问（Grilling）

## 机制：设计树、轮次与前沿

像面试官一样持续盘问用户，直到双方达成共识。把整个过程映射为一棵**设计树（design tree）**：每个决策都会分叉出挂在它之下的子决策。

以**轮（rounds）**为单位推进这棵树。**前沿（frontier）**指所有前置条件已经敲定的决策——也就是你**现在**就能问的问题，不必猜测你还没听到的答案。每轮只问一个问题：从前沿中挑一个，给问题编号并给出你的推荐答案。等用户回答完，再进入下一轮。

每一轮，用户的回答都会重塑这棵树——已敲定的决策把前沿向外推，解开依赖它们的后续问题。重新计算前沿，进入下一轮。某个问题的答案如果依赖本轮尚未回答的问题，它属于**更晚**的轮次，而不是本轮。

## 提问格式与编号纪律

每个问题都应按如下格式：

```
**Q1** - **<问题标题>**：<问题正文，可以是多段，包含多个选项>

**推荐答案**：<你的推荐答案>
```

编号纪律：问题编号 Q1、Q2…全局连续递增，不跳号不复用；问题内多个选项统一用 A、B、C…编号，推荐答案引用时写“推荐 A：理由”；引用前置结论写“Q{m} 的结论”，不复述旧问题。

**推导决定（D 系列）**：从已敲定回答中逻辑推导出的结论——无需再问，但必须让用户知情。编号 D1、D2…与 Q 系列独立递增。每轮把新产生的推导决定列在问题之前，格式：

```
**D1** - **<决定标题>**：<结论>（由 Q{m} 推导）
```

D 默认采纳，用户可指出异议；若被推翻，把推导链中未明说的前提升格为新的 Q 问题重新走查。

## 事实与决策分工

查**事实**是你的职责，绝不是用户的。当前沿问题需要环境中的事实（文件系统、工具等）时，派一个子代理去查——凡是你能自己查到的东西，都别去问用户。不要卡在它上面：一次进行中的探查是一个未敲定的前置条件，因此只有它下游的问题才需要等子代理汇报——先问前沿中不需要等事实的问题，需要事实的等汇报后再问。**决策**属于用户——逐条抛给他们，然后等待。

## 完成与收尾

当前沿为空时，会话才算结束：设计树的每个分支都已走查过，没有留下任何被默默假设的东西。此时停下，把已敲定的决策按 Q 与 D 编号列成清单，请用户确认共识，并让用户选择下一步：开始实施 / 继续盘问 / 调整决策。用户做出选择前，不要基于共识采取行动。
