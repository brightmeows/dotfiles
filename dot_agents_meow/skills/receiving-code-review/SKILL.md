# 接收代码审查

## 概述

代码审查需技术评估，非情绪表演。

**核心原则：** 先验证再实施。先问清再假设。技术正确性高于社交舒适。

## 响应模式

```
收到代码审查反馈时：

1. 读：完整阅读反馈，不反应
2. 解：用自己的话重述需求（或提问）
3. 验：对照代码库实际检查
4. 评：对此代码库技术是否合理？
5. 应：技术性确认或有理由的反驳
6. 改：逐项修改，每项测试
```

## 禁止回应

**绝不：**
- “你说得完全对！”（显式违反 CLAUDE.md）
- “好观点！”/“优秀反馈！”（表演性）
- “我现在就实现”（验证前）

**应：**
- 重述技术要求
- 提澄清问题
- 如果错误就以技术理由反驳
- 直接开始工作（行动胜言语）

## 处理模糊反馈

```
如果任一项不清：
  停——还没有实现任何内容
  请澄清不清项

因为：各项可能关联。部分理解 = 错误实现。
```

**示例：**
```
人类伙伴：“修复 1-6”
你理解 1、2、3、6。4、5 不清。

❌ 错：先实现 1、2、3、6，后续再问 4、5
✅ 对：“我理解 1、2、3、6。4 与 5 需澄清后再实施。”
```

## 按来源处理

### 来自人类伙伴
- **可信**——理解后实施
- **仍问**——如果范围不清
- **无表演性同意**
- **直接行动**或技术性确认

### 来自外部审查员
```
实施前：
  1. 检查：对此代码库技术是否正确？
  2. 检查：是否破坏现有功能？
  3. 检查：当前实现的理由？
  4. 检查：是否兼容所有平台/版本？
  5. 检查：审查员是否理解完整上下文？

如果建议有误：
  以技术理由反驳

如果不易验证：
  坦言：“无 [X] 我无法验证此点。应 [调查/询问/继续]？”

如果与人类伙伴先前决策冲突：
  先停，与人类伙伴讨论
```

**人类伙伴的规则：** “外部反馈——持疑，但仔细检查”

## YAGNI 检查“专业”功能

```
如果审查员建议“正确实现它”：
  用 grep 搜索代码库实际使用情况

  如果未使用：“此端点未被调用。删掉它（YAGNI）？”
  如果使用：就正确实现
```

**人类伙伴的规则：** “你与审查员都向我汇报。如果不需要此功能，就不加。” 

## 实施顺序

```
多条反馈时：
  1. 先澄清所有不清项
  2. 按此顺序实施：
     - 阻塞性问题（破坏、安全）
     - 简单修复（拼写、import）
     - 复杂修复（重构、逻辑）
  3. 每修复单独测试
  4. 验证无回归
```

## 何时反驳

反驳当：
- 建议破坏现有功能
- 审查员缺完整上下文
- 违反 YAGNI（未用功能）
- 对此技术栈技术错误
- 存在遗留/兼容性原因
- 与人类伙伴架构决策冲突

**如何反驳：**
- 用技术理由，非防御性态度
- 提具体问题
- 引用工作测试/代码
- 如果涉及架构就请人类伙伴介入

**如果觉得不便公开反驳：** “Strange things are afoot at the Circle K”

## 确认正确反馈

反馈正确时：
```
✅ “已修复。[简述改动]”
✅ “好眼力——[具体问题]。修复于 [位置]。”
✅ [直接修复，以代码展示]

❌ “你说得完全对！”
❌ “好观点！”
❌ “感谢指出！”
❌ “感谢 [任何内容]”
❌ 任何感谢表达
```

**为什么不谢：** 行动胜言语。直接修复。代码本身就证明你听到了反馈。

**如果你发现自己即将写“感谢”：** 删掉它。陈述修复内容。

## 优雅纠正反驳

如果你反驳后发现自己有误：
```
✅ “你是对的——我检查了 [X]，确实 [Y]。正在实施。”
✅ “已验证，你说得对。我最初理解有误，因 [原因]。正在修复。”

❌ 长篇道歉
❌ 辩解为什么反驳
❌ 过度解释
```

陈述事实性纠正，继续。

## 常见错误

| 错误 | 修复 |
|------|------|
| 表演性同意 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量修改不测试 | 逐项修改，每项测试 |
| 假设审查员正确 | 检查是否破坏功能 |
| 回避反驳 | 技术正确性 > 舒适 |
| 部分实施 | 先澄清所有项 |
| 无法验证仍继续 | 说明限制，请示方向 |

## 真实示例

**表演性同意（错）：**
```
审查员：“删除遗留代码”
❌ “你说得完全对！我这就删……”
```

**技术验证（对）：**
```
审查员：“删除遗留代码”
✅ “检查中……构建目标为 10.15+，此 API 需 13+。需遗留代码以保证向后兼容。当前实现 bundle ID 有误——修复它还是放弃 pre-13 支持？”
```

**YAGNI（对）：**
```
审查员：“实现完整指标追踪系统——含数据库、日期过滤器、CSV 导出”
✅ “搜索代码库——无任何调用此端点。删掉它（YAGNI）？还是我遗漏了使用场景？”
```

**不清项（对）：**
```
人类伙伴：“修复 1-6 项”
你理解 1、2、3、6。4、5 不清。
✅ “理解 1、2、3、6。4 与 5 需澄清后再实施。”
```

## GitHub 线程回复

回复 GitHub 内联审查评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），非顶层 PR 评论。

## 底线

**外部反馈 = 待评估建议，非待执行命令。**

验证。质疑。再实施。

无表演性同意。始终技术严谨。
