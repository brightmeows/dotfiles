# 对抗合理化——详细参考

> writing-skills 技能中“跳过测试的常见合理化借口”与“让技能防弹——对抗合理化”两节的完整参考。SKILL.md 仅保留核心手法摘要，需要借口对照表、完整封堵手法、合理化表与红旗清单模板时读本文件。

## 跳过测试的常见合理化借口

| 借口 | 事实 |
|-----|------|
| “技能显然很清楚” | 你觉得清楚 ≠ 其他 agent 觉得清楚。测试它。 |
| “只是参考而已” | 参考可能有缺口、不清晰的章节。测试检索。 |
| “测试是大炮打蚊子” | 未经测试的技能总有问题。15 分钟测试节省数小时。 |
| “出问题再测” | 出问题 = agent 无法使用技能。部署前测试。 |
| “测试太繁琐” | 测试比在生产中调试糟糕的技能更不繁琐。 |
| “我有信心没问题” | 过度自信保证有问题。无论如何都测试。 |
| “学术审查就够了” | 阅读 ≠ 使用。测试应用场景。 |
| “没时间测试” | 部署未经测试的技能浪费更多时间之后修复。 |

**这些都意味着：部署前测试。无例外。**

## 让技能防弹——对抗合理化

执行纪律的技能（如 TDD）需要抵抗合理化。agent 很聪明，在压力下会找到漏洞。

**心理学笔记：** 理解说服技术为何有效，帮助你系统化地应用它们。研究基础见 persuasion-principles.md（Cialdini, 2021; Meincke et al., 2025）中的权威、承诺、稀缺性、社会认同和统一性原则。

### 明确封堵每个漏洞

不要只说规则——要禁止具体的变通方法：

<坏>
```markdown
先写代码后写测试？删除它。
```
</坏>

<好>
```markdown
先写代码后写测试？删除它。重新开始。

**无例外：**
- 不要将它作为“参考”保留
- 不要在写测试时“适配”它
- 不要看它
- 删除就是删除
```
</好>

### 应对“精神 vs 文字”论调

尽早增加根本原则：

```markdown
**违反规则的字面含义就是在违反规则的精神。**
```

这切断了整类“我遵循的是精神”的合理化。

### 建立合理化表

从基线测试中捕获合理化借口（见下面的测试章节）。agent 的每一个借口都放入表中：

```markdown
| 借口 | 事实 |
|-----|------|
| “简单到不用测” | 简单代码也会坏。测试只需 30 秒。 |
| “我之后会测” | 立即通过的测试证明不了什么。 |
| “后写测试也能达到相同目标” | 后写测试 = “这做了什么？” 先写测试 = “这应该做什么？” |
```

### 创建红旗清单

让 agent 在合理化时能自我检查：

```markdown
## 红旗——停止并重新开始

- 先写代码后写测试
- “我已经手动测试过了”
- “过后写测试也能达到相同目的”
- “这是关于精神而非仪式”
- “这不一样，因为……”

**这些都意味着：删除代码。用 TDD 重新开始。**
```

### 更新 CSO 加入违规症状

在 description 中加入：你即将违反规则时的症状：

```yaml
description: 在实现任何功能或修复 bug 时、编写实现代码前使用
```
